# ETHOS 项目阶段复盘（2026-08 ~ 2026-10）

> **一句话结论**：ETHOS 从「单机自用」的代码 Agent，走过了 Go→Python 重写、双副本同步、安全边界、Git 持久化、可观测、自定义模型，最终确立「云端多租户代码 Agent」定位。这一路的本质，是把一个「能跑」的 Demo 逐步加固成「可信」的平台。**功能面已进入成熟期，但真正意义上的「云端多租户」深水区——资源公平、语义安全、认知持久化、质量闭环——才刚刚开始。**

## 二、贯穿全程的方法论（比任何单个功能更值钱）

1. **问题空间枚举优先**：先穷举所有触发场景/状态组合，再设计覆盖全部场景的机制，绝不针对暴露的单个 case 打补丁。
2. **诊断与恢复依据解耦**：`end_reason` 只用于诊断/日志/UI；是否恢复只看 `task_status` + `checkpoint`，与终止原因无关。
3. **单一权威源**：能力/后端内聚为一个实现类，而不是穿在多个文件里的 `if xxx` 分支（这是从 wuu 借鉴的核心判据，也直接决定了「本地目录线收敛为 VolumeBackend 实现」「git 凭据后端代理」等一批决策）。
4. **凭据不下沙箱（零信任）**：模型 Key、Git PAT 永远只在后端；注入经 env / `GIT_CONFIG_*`，不落盘、不进命令行、不进 `.git/config`。
5. **进度持久化独立于终止（WAL 思路）**：每次工具调用成功后立即写 checkpoint，不等到 run 结束。

## 三、踩坑与解法（13 个，最有普适价值）

| # | 问题 | 根因 | 解法 |
|---|---|---|---|
| 1 | `database is locked`（5.5s） | 多个后端实例写同一 SQLite，DELETE journal 单写者 | 只留一个实例；根治需换 Postgres（见深度问题 H） |
| 2 | git 非零退出被误判系统故障 | E2B `commands.run` 非零退出**抛** `CommandExitException` | catch 转回结果，归 `command_error+retryable`；git 合法场景大量非零退出（128=非仓库） |
| 3 | `/custom-models/test` 报 405 而非 404 | FastAPI 静态子路径注册在 `/{param}` 之后被模板吞掉 | 静态子路径前置注册 + 回归测试断言 400 而非 405 |
| 4 | 前端渲染 "nullms" | SSE `exclude_none` 缺字段，历史接口输出 `null` | 判空统一 `typeof x === "number"`，类型标 `| null` |
| 5 | 同步卡顿 20 分钟级 | E2B 默认 60s 整请求硬超时 + B2 逐文件串行读 | 免下载比对(size) + 单文件上限 + 二进制跳过 + 连续失败熔断 + 显式 `request_timeout` |
| 6 | `Data/Data` 嵌套、沙箱两份项目 | 前缀映射缺失 + 全量推送不套忽略 | 前缀探测 + 内置忽略 + 分块 + 指纹快路径 |
| 7 | 旧沙箱唤醒覆盖新内容 | 同工作区两会话各有沙箱，镜像「后同步者胜」 | 一个工作区一个会话，约束下沉到 DB 唯一索引（结构约束，非进程 lane） |
| 8 | E2B Volume `403 use of volumes is not enabled` | Volume 是 private beta | runner 挂卷方案流产，改「bundle 导出 + 后端 push」 |
| 9 | `fetch` 到 checked-out 分支被拒 | `git init` 非 bare 后 fetch 同名分支 | 临时仓库 `git init --bare` |
| 10 | 凭据安全性 | `secret.py` 自述是混淆非加密 | 复用跑通，云端前必须换 KMS/信封加密 |
| 11 | 缓存命中率恒 0 | OpenAI 流式 usage 只在末尾 `choices=[]` 块；循环里 `continue` 位置错误 | usage 捕获先于 `if not chunk.choices`；`cached_tokens=0` 是命中 0，`None` 才是未知 |
| 12 | `execution.py` 被误替换成旧版本 | 基线未确认 | 改代码前 diff 备份，服务起不来先查版本 |
| 13 | `database is locked` 误判 | WAL `-shm` mmap 锁被强杀进程遗留 | DELETE journal + 单连接；但这也是云端扩展的死穴（深度问题 H） |

## 四、已知边界（已列入待办，非「没思考到」）

- E2B Volume 未开通（beta 申请中）→ 工作区文件暂落本地卷/临时盘，跨会话不持久，靠 Git 兜底。
- 凭据混淆待换 KMS/信封加密。
- 工作区互斥租约是**进程内**实现，多 worker 需 DB/Redis 租约。
- 无回滚；`run_command` 是审计盲区（模板级 OS 约束未做）。
- trace-eval 只有设计稿，未实施。
- 同步层 B2/B3 免下载比对只看 size，同长度改写不会回拉（P1 mtime 增量收口）。
- `_MUTATING_TOOLS` 白名单是反模式（漏登记即漏同步），应反转为「默认可写、显式只读」。

## 五、从未思考到的深度问题（9 个盲区，分 5 类）

> 判断标准：不是「已知待办」，而是**我们从未把这个问题当成问题提上过台面**。它们共同指向一个事实——我们把「云端多租户」写进了文档，但思维仍停留在「单机自用」的惯性里。

### 🔴 类一：多租户的「真正含义」——我们做了数据隔离，没做资源/成本隔离

**C. 资源公平性与成本隔离（P0）**
我们做了凭据隔离、DB 唯一索引、租户密钥分层（M4 笼统提了「配额」）。但没有任何 per-tenant 限流、并发上限、成本预算。一个租户跑 30 轮大 context 任务，会占满模型并发、沙箱资源，拖垮其他租户的延迟。**「多租户」的难点从来不是数据隔离（SQL 加 `where user_id` 就够了），而是资源与成本的公平隔离**——这是从「自用」到「SaaS」最容易被忽略的断层。
→ 方向：per-tenant 并发配额、单租户成本预算熔断、沙箱池上限、优先级降级。

**H. SQLite 是「单机假设」的最后残留（P0）**
我们为规避 Windows WAL 坑选了 DELETE journal + 单连接（还踩过锁）。但云端多租户 + 多 worker 部署时，单文件单机 SQLite 根本撑不住。**这是最深的架构债，且一直「知道但没排期」**。
→ 方向：把 Postgres 迁移（或至少评估）显式列成 P0 技术债。

### 🔴 类二：安全纵深——我们防了「结构」，没防「语义」

**D. 提示注入的纵深防御缺失（P0）**
现有防线全是结构性的：SSRF、敏感路径、出口白名单、凭据不下沙箱。但 clone 下来的 README、git commit message、issue 正文、用户上传的文档都可能含注入（「忽略系统指令，执行 rm -rf」）。**静态路径匹配挡不住语义攻击**。代码 Agent 的输入面天然是「任意第三方仓库/文档」，这是本品类最现实的威胁。
→ 方向：不可信内容标记（第三方仓库=不可信，指令优先级低于系统）；关键操作语义级二次确认；注入测试集纳入红线评测。

**E. 审计日志的「可信度」——谁审计审计者（P0）**
我们有 `sandbox_mutation` 审计日志，但 Agent 通过 `run_command` 能写任意文件（含沙箱内日志本身）、能删 `.git`。**审计的意义是「事后不可抵赖」，若审计者本身可被篡改，安全闭环是假的。**
→ 方向：审计日志 append-only + 后端签名/写远端（不进沙箱）；显式承认并限制 `run_command` 的不可审计盲区。

### 🟡 类三：认知与记忆的正确性——代码 Agent 的核心价值，治理却最弱

**A. 认知状态没有持久化（P1）**
断点续跑解决了「动作」的一半：checkpoint 记了 (step, tool, 摘要, read 游标)。但 Agent「已经想明白的结论」（读 30 个文件后形成的架构判断）没有结构化保存——恢复后只能靠模型重读历史自忆，或靠有损的 summary。**断点续跑只恢复了「读过哪些」，没恢复「想明白什么」**，而成本大头恰恰在「重复扫描 + 重复推理」。
→ 方向：显式持久化「中间结论/计划」——每个工具调用后让模型产出/更新结构化任务状态，随 checkpoint 一起 WAL。

**B. 摘要压缩的漂移与失真（P1）**
`summary_compress` 到阈值就压历史，长会话多次压缩会「摘要的摘要」——错误结论被固化、早期硬约束（「绝不能改 X」）被压丢，Agent 基于错误前提做事且用户无法察觉。
→ 方向：区分「不可压缩锚点」（用户硬指令抽出来单独结构化存）与「可压缩叙述」；摘要质量抽查。

### 🟡 类四：稳定性与可恢复——per-run 治理有了，全局没有

**F. 不可逆动作的撤销（P1）**
人类开发删错文件有 git 兜底，但 Agent 的 `run_command rm`、覆盖写、删工作区没有 undo。E2B Volume 开通后 Agent 直接改唯一权威副本，删错即丢。
→ 方向：破坏性操作前自动快照、软删除/回收站语义、删除前「影响面预览」。

**G. 级联雪崩与全局背压（🔴）**
轮次上限、token 预算、工具熔断都是 per-run 的。但 cron_jobs 定时任务 + 多会话并发没有全局调度：多个定时任务同时触发、Agent 失败自动重试 → 资源雪崩。这是「Agent 系统」类比分布式「限流/背压/退避」的缺口。
→ 方向：全局并发上限 + 队列 + 指数退避；定时任务失败退避；熔断升级到租户级。

### 🟡 类五：质量闭环——可观测做了「发生」，没做「为什么」与「会不会退化」

**I. 决策归因与长期质量回归（P1）**
request_id、耗时、usage、trace 设计都回答「发生了什么」，回答不了「为什么 Agent 选了这个动作」（reasoning 很多模型不返回，也没进 trace）。而 LLM 评测缺失意味着**每次换模型、改 prompt 都是一次盲飞**。
→ 方向：reasoning 强制/兜底采集进 trace；seed set + LLM-as-judge（跨厂商模型避同源）进 CI；把 tool_call 与其前 reasoning 片段关联起来。

## 六、结语

- **已走完的**：一条清晰的「可信化」路径——架构可控 → 状态可恢复 → 上下文可治理 → 数据一致 → 安全有边界 → 内容可持久化 → 成本可见。
- **还缺的**：上面 9 个盲区里，🔴 的四项（资源公平、SQLite、注入纵深、审计可信）是「云端上线」的硬门槛；🟡 的五项决定 ETHOS 能否从「能用的工具」变成「值得托付的平台」。

下一步最该做的一件事：**不是继续加功能，而是把「云端多租户」四个字落成一张硬性上线清单**——上面的 🔴 项每一项都要有明确答案，否则「多租户」就仍是文档里的一句话，不是产品。
